# M11 — Multi-Raft

`docs/DESIGN.md` §M11 and the roadmap's M11 section are the spec. This file
records the decisions that milestone leaves open, and the order the work goes
in. As with M10, the roadmap deliberately stopped short of step level because
the shard-router interface had to be decided here.

## What M11 delivers

- Many Raft groups per node — one per shard this node replicates — over **one
  shared tick loop**, not one task or thread per shard.
- Per-shard Bitcask instances: `<data-dir>/shards/{id:05}/{raft,state}`.
- A router: key → shard → this node's group, or `NotHosted` naming the nodes
  that do hold it.
- A transport that carries every group's traffic over **one connection per
  peer**, batched, instead of one connection per (peer, group).
- A client that caches the shard map, routes by it, and invalidates on
  `NotHosted`.

Not in M11: moving data when placement changes (M12). A shard group is founded
once, from the map the node first saw, and a later map version that reassigns
it is logged rather than acted on.

## Decisions

### The single data group becomes shard 0's group, and nothing is migrated

`group::DATA` was already numbered `shard(0)` so that M11 would inherit the
numbering. It now stops being special: a node hosts a group per shard it
replicates, each in its own directory.

A store written before M11 has one log under `<data-dir>/raft` holding keys
from all 256 shards, and no correct way to split it without a data move —
which is M12's migration driver, not something a startup path can do. So a
node that finds the pre-M11 layout **refuses to start** and says why. Silently
ignoring a directory that holds the entire previous dataset is data loss
wearing the costume of an empty database.

### One tick loop, and the meta group keeps its own

`Driver` stops owning one group and owns `BTreeMap<GroupId, Group>`: one
`interval`, one `select!`, and a drain per group. 256 shards × one task each is
the naive design this milestone exists to avoid, and the comment in `run()`
says so.

`main` runs **two** drivers, not one: the meta group in its own, every shard
group in another. The meta group is the routing authority for the whole node —
a shard's snapshot scan must not stall the map. That still satisfies "not one
thread per shard", and it keeps `Driver` honest as a 1..N host rather than
making "the meta group" a case inside it.

### Transport: one connection per peer, group per message, batched

`PeerConfig.group` goes away. `PeerLink::try_send` takes `(group, msg)`, the
per-peer queue carries the pair, and the reply channel carries
`(group, peer, msg)` so the driver can route a response to the group that
asked.

That alone is not enough. The sender loop awaits a round trip per message, so
one link is capped at roughly one message per RTT — and a node hosting 154
shard groups (256 shards, RF 3, 5 nodes) must heartbeat all of them inside one
election timeout. So the loop drains its queue with `recv_many` and sends one
`Batch` RPC carrying every queued envelope, taking one RTT per batch instead
of per message. This is TiKV's `BatchRaftMessage` for the same reason.

The four unary RPCs stay: the server still has to accept them (older peers,
and the single-group transport tests), and `Batch` is implemented by fanning
out to the same per-group inboxes and collecting every group's reply.

A response message carries no group of its own, so the envelope carries it
explicitly rather than relying on the request field.

### A shard group is founded once, from the first map this node sees

Placement is replicated, so every replica of shard S computes the same replica
set from the same map version and can found S's group with no conf change —
*provided they all use the same version*. They do not, in general: a map
version that moves a replica slot would have the newcomer found a group with
different voters than the incumbents are already running. Two configurations
for one shard is split brain.

So founding is a one-time act, recorded durably:

- A founding node (no `--join`), the first time a map is published, creates a
  group for every shard the map gives it and writes
  `<data-dir>/shards/.placement` with that map version.
- Every later boot hosts exactly the shards on disk.
- A node started with `--join` founds **nothing** and writes the marker
  immediately. It hosts shards only once M12's migration adds it as a learner.
- A map that later assigns us a shard we do not host, or takes one we do, is
  logged once and otherwise ignored. Migration is M12.

### Late nodes join the meta group as permanent learners

M10 left this open and it has to be settled here: the meta group's membership
is the founding `--peer` set, so a node admitted afterwards has no local map —
it cannot route, cannot answer `NotHosted` with a hint, and cannot learn which
shards it holds.

The reconciler, running on the meta leader, proposes `AddNode` to the *meta*
group for any data-cluster member that is not a meta member. They stay
learners forever: `Group` gains `promote_learners`, false for the meta group,
so `maybe_promote` cannot grow the meta quorum with the data cluster. That is
the route M10's plan recommended, and it is why learner `match_index` tracking
exists.

### Routing, and what a misrouted request is told

`router.rs` is a pure function over the published map:

```rust
pub enum Route {
    Local(ShardId),
    Elsewhere { shard: ShardId, replicas: Vec<NodeId> },
    NoMap,
}
```

`KvApi` resolves it before the driver sees the request. `Elsewhere` becomes
`NotHosted { shard, replicas, map_version }` on the wire — an ordinary answer,
like `NotLeader`, not an error, because a client that gets an error drops the
connection instead of following the redirect. `NoMap` is `unavailable`: the
node genuinely cannot say where the key belongs yet.

`ClientRequest` carries the shard, and the driver answers `NotHosted` too if it
turns out not to host it — the service's map can be a version behind its own
driver.

`ClusterStatusResponse.shards` finally gets filled: per-shard leader and
replica set, which is what makes "writes to different shards land on different
leaders" observable rather than asserted.

### The client caches the map and invalidates on `NotHosted`

`kv-client` gains `kv-ring` (pure, and already depended on by nothing impure),
a cached `ShardMap`, per-shard leader cache, and an endpoint book learned from
`ClusterStatus`. A `NotHosted` refreshes the map and retries; a `NotLeader`
follows the hint for that shard alone, so one shard's failover no longer
throws away every other shard's cached leader.

### The file-descriptor budget is checked at startup

Per-shard Bitcask means two engines per hosted shard, each holding an fd per
segment. A node hosting 154 shards needs over a thousand descriptors before it
serves a single client, and the usual default is 1024 — so the node raises
`RLIMIT_NOFILE` to its hard limit at startup, like every other database, and
refuses to start when even that cannot cover the shards it is about to open,
naming the limit to set.

## Order of work

Strict TDD, one commit per step.

- **M11.1** `ShardId` and the per-shard layout: `NodeConfig::shard_raft_dir`/
  `shard_state_dir`, the `.placement` marker, and the refusal on a pre-M11
  store.
- **M11.2** Transport multiplexing: group per message, one link per peer,
  `(group, peer, msg)` replies. All existing tests pass through the new shape.
- **M11.3** The `Batch` RPC: envelope, sender-side coalescing, server-side
  fan-out and reply collection.
- **M11.4** `Driver` becomes multi-group: extract `Group`, one ticker, drain
  every group. Two drivers in `main`, one for meta and one for shards.
- **M11.5** Shard founding from the published map, with the one-time marker
  and the `--join` rule.
- **M11.6** The router, `NotHosted`, and `ShardStatus` in `ClusterStatus`.
- **M11.7** `kv-client`: map cache, per-shard leaders, invalidation.
- **M11.8** fd budget: raise the soft limit, refuse an impossible one.
- **M11.9** The gate. The in-process harness generalizes from three hard-coded
  nodes to `Cluster::of(nodes, shards, rf)`.

## ✅ criteria (from DESIGN.md)

- 5 nodes × 3 replicas × 8 shards: writes to different shards land on
  different leaders and proceed concurrently.
- Killing a node degrades only the shards it led, and only briefly.

---

## What landed

All nine steps and both ✅ criteria, as `tests::multi_raft::the_m11_gate`.
378 tests pass (was 371 before the gate, 369 before M11) on both read engines;
`cargo fmt --check` and `cargo clippy --workspace --all-targets -D warnings`
are clean; M4's 10k-seed election gate passes in 0.93s. `kv-raft` and `kv-sim`
were not touched, so M11 adds nothing to the nemesis-sweep gap M8/M9 already
carry.

Measured on a real three-node cluster at the default 256 shards, release
build: **~5% of a core per node** idle, 0 write failures in 40 keys, every
shard led. Debug build, ~30%.

### Things that came out differently from the plan

**The meta-learner reconciliation was unnecessary.** The plan had the
reconciler propose `AddNode` to the meta group for any data-cluster member
missing from it. But once there is no single data group, the meta group *is*
the cluster's membership authority — so `AdminService::AddNode` simply sends
there, and there is nothing left to reconcile. What did survive is the other
half: `Group::promote_learners`, false for the meta group, so a node admitted
after bootstrap replicates the map forever and never joins the meta quorum.

M10's `a_learner_is_not_given_shards` inverted with it, and is now
`a_node_admitted_after_bootstrap_is_placed_and_never_votes`. The old rule —
placement from voters only — was right when a learner was catching up on user
data. A meta learner is a full cluster member that only ever learns placement,
and excluding them would mean a node admitted after bootstrap never appeared
in the map at all: it could not route, could not be routed to, and could never
receive a shard.

**The fd budget reports rather than refuses.** The plan said refuse when the
limit cannot cover the shards about to be opened. It cannot know that: the
hosted shard count is the map's answer and the map arrives after startup.
So the node raises `RLIMIT_NOFILE` to its hard limit and logs what it got —
measured at 531 descriptors for 256 shards, against a common soft default of
1024.

### Two bugs the test suite could not see

Both were found by running a real cluster at the default shard count and
measuring it. Every in-process test hosts one shard, so neither showed up in
378 passing tests.

**Reconciliation was O(groups) per message.** `Driver::drain` reconciled the
shared peer links after *every* drain, walking every group to build the union
of their memberships. Free with one group; 256 group visits per inbound
message with 256 of them. A three-node cluster sat at **120% of a core per
node** and left about a tenth of its shards **permanently** leaderless,
thrashing elections at term 60+, because the loop could not keep up with its
own ticks. Now it runs when membership actually moves — a conf entry applied
or a snapshot installed, which `Group::drain` reports — plus a one-second
sweep for a link that could not be opened when it was first wanted.

`tests::multi_raft::every_shard_elects_a_leader_when_one_loop_drives_many` is
the guard, and its shard count is load-bearing: at 64 shards it passes with
the bug still in, because the in-process harness has no serialization cost. At
256 it passes in 0.3s and times out at 30s without the fix.

**The per-peer queue was a constant.** 64 slots against 256 groups. One link
carries every group's traffic and a drain can put one message per group on
it, so a shallower queue sheds *some* group's message every drain — and which
group loses is a race the loser keeps losing: no leader means campaigning,
campaigning means more traffic, more traffic means more shedding. It never
converges. `NodeConfig::peer_queue_depth` is now `64 + 2 * num_shards`. This
one was contributory rather than sufficient: fixing it alone took the
leaderless set from 25 shards to 15.

### One client change the gate forced

`RETRY_ROUNDS` went from 40 to 120. A single-group cluster became writable as
soon as one election finished; a sharded one elects a meta leader, publishes a
placement, founds its shard groups and *then* elects within the key's shard. A
client that gave up inside two seconds reported a cluster that was starting
normally as unreachable — which is what an operator's first write after
bringing a cluster up would have hit.

The three-process gate passes `--shards 4`. It is about three real processes
surviving a `kill -9`, not about how many Raft groups one box can tick.

## Not done, deliberately

- **Moving data when placement changes.** A shard group is founded once and
  never reconfigured, so a map version that reassigns a shard is logged and
  otherwise ignored. That is M12's migration driver, and the divergence is
  reported per shard, once, by `shards::ShardSupervisor::report_divergence`.
- **`Rebalance`/`VerifyShard`** still answer `unimplemented`. M12.
- **Wait-free reads.** M11.5's `left-right` keydir is untouched; reads still
  funnel through each shard's driver. There are now many drivers rather than
  one, so the funnel is per shard instead of per node — which is most of what
  M11 buys the read path.
- **`docs/DESIGN.md` and `CLAUDE.md` still describe the single data group**,
  along with M8's and M9's state. M8, M9 and M10 were never committed either,
  so bringing those two files up to date belongs with whatever commit finally
  lands this work rather than with M11 alone.
