## What M11 changed under M11.5's feet

M11.5 was specified before M11 existed. Four of its assumptions have moved.

**1. There is no single driver any more.** `kv-node/src/driver.rs` has split
into `Group` (one Raft group: its `RaftNode`, its `Engine`, its pending
requests, its applied index) and `Driver` (a map of `Group`s, one `interval`,
one `select!`). `main` runs two drivers: the meta group alone, and every shard
group in the other. So "the apply loop" M11.5 talks about is now
`Group::drain`, and there is one keydir **per shard**, not one per node.

That is mostly good news for M11.5: the write side is still a single owner per
keydir, which is exactly what `left-right` requires. But `published_index` is
per group, and the ReadIndex wait that must change is in
`Group::serve_ready_reads` / `Group::begin_read`, not in one place.

**2. Reads already left the Raft loop, through `io_uring`.**
`kv-node/src/read_engine.rs` is the read path: `Group::answer_read` resolves
the keydir lookup on the driver (`Engine::locate` → `ValueRef`) and submits
the *disk* half to a shared ring, or to a blocking pool where no ring is
available. CI runs the whole suite twice, once with
`BOHIME_READ_ENGINE=blocking`, and that second arm must stay green.

So the thing M11.5 removes is **not** "reads block the loop" — that is gone.
It is the remaining funnel: the keydir lookup still happens on the driver
task, one request at a time, because `Engine::put` mutates both the keydir and
the segment map and a reader cannot hold `&Engine` across that. `left-right`
on the keydir plus `ArcSwap` (or equivalent) on the segment handles is what
removes it.

**3. `Engine::get` already takes `&self`.** The read is `pread`
(`read_exact_at`), not `seek`+`read`, so there is no shared cursor and N
readers can share a `&Engine` for the read itself. `Engine::locate(&self,
key) -> Option<ValueRef>` is the external-I/O seam; `ValueRef` carries a raw
fd, an offset, a length and an `Arc<SegmentMap>` keepalive.

**4. The `KeyDirIndex` seam is intact and narrow.**
`crates/kv-storage/src/index.rs` has five methods — `get`, `insert`, `remove`,
`relocate`, `iter` — and `engine.rs` touches the index at exactly six call
sites (`put`, `get`, `locate`, `scan`, `delete`, and `compact`'s relocate
loop). M11.5's task 1 says no call site in `engine.rs` should have to change,
and that still looks achievable. If one does have to change, the seam was
wrong and that is worth reporting rather than working around.

## The finding that decides whether M11.5's gate tells the truth

From the read-path handoff, measured with criterion and an isolated pread
diagnostic, on an i9-12900H (20 logical / 14 heterogeneous physical cores, so
20× never existed; a syscall-free control arm tops out at 11.2×):

| | 1 thr | 8 thr | 20 thr | 1→20 |
|---|---|---|---|---|
| memcpy control | 15.60 | 63.68 | 94.47 | 6.1× |
| all threads share one `File` | 2.16 | 6.39 | **6.42** | **3.0×** |
| one fd each, same inode | 2.04 | 11.42 | 16.78 | 8.2× |
| one file each | 2.30 | 12.61 | 17.36 | 7.5× |

`Engine::get` under N threads reaches 0.83 → 6.70 Melem/s from 1 → 16 threads
and then **goes flat**, sitting exactly on the shared-handle ceiling.

**`left-right` fixes the keydir. The keydir is not what caps this curve.** One
`Arc<File>` per segment plateaus at ~6.4M reads/s however many cores you add,
because every `pread` goes through `fget` on a `struct file` shared by every
reader (`f_count`, plus the per-handle readahead state `f_ra`). Per-fd ≈
per-file in the table above, so the *inode* is not the contention point.

M11.5's headline gate is "read throughput vs. core count (1→20) for
`RwLock<HashMap>`, `DashMap`, and left-right — the scaling graph goes in the
README." **Build that graph without fixing the file handle first and it will
be flat for all three arms, and the README will blame the wrong thing.**
Either fix the handle as part of this milestone (per-reader fds, or `io_uring`
with `IORING_REGISTER_FILES` — `read_engine.rs` already registers nothing) or
publish the graph with the ceiling named and the handle experiment beside it.

A second, self-inflicted ceiling arrives at the same time: `Engine::locate`
clones `Arc<SegmentMap>` per call, so under N threads it contends on one
refcount and saturates at 14.7 Mops/s from 8 threads (flat to 20). It does not
bite today because `locate` runs only on the single driver task. It becomes a
ceiling the moment reads move fully off the driver, which is precisely what
M11.5 does.

## M11.5's real correctness trap

Not `left-right` itself — the **ReadIndex wait**. `last_applied` advances when
an op is *absorbed*; readers do not see it until `publish()`. A read that
waits on `last_applied` and then reads a `ReadHandle` can miss a write that
has already been acknowledged to the client. §1.15 calls this out and the
gate insists on the order: write the stale-read test against the naive
`last_applied` wait **first**, watch it fail, then introduce
`published_index`. That failure is the milestone's whole story.

In the current code the wait is `PendingRead::confirmed_at <= applied_index`
in `Group::serve_ready_reads`, and `applied_index` is set in `Group::drain`
after each committed entry reaches the `Engine`.

## Benchmarking traps on this machine, measured

1. **`/tmp` is tmpfs.** Any bench using `tempfile::tempdir()` measures memory
   and its fsync is a no-op. `crates/kv-storage/benches/engine.rs`'s
   fsync-policy arm does exactly this, so its `every_write` number is not
   measuring fsync — a pre-existing bug in a bench someone may have drawn
   conclusions from. `benches/read_scaling.rs` uses `CARGO_TARGET_TMPDIR`
   instead; copy that.
2. **`/home` is btrfs with `compress=zstd:3`.** Benchmark values must be
   pseudo-random or cold-read numbers are fiction.
3. Threads are not pinned and the governor ramps with load, so the 1-thread
   and 20-thread points run at different clocks. Treat ratios as approximate;
   run-to-run spread was ~±7%.

## Constraints that are not negotiable

- **TDD, and the repo means it.** Failing test first, confirm it fails for the
  expected reason, then implement. Both bugs M11 found were found by measuring
  a real cluster *after* 378 tests passed, so a green suite is not evidence.
- **Test placement.** No inline tests, no `mod tests;` tail on a source file.
  Tests live in `src/tests/<name>.rs`, declared in `src/tests/mod.rs`, reached
  by absolute `crate::` paths — never `use super::*`.
- **The purity boundary.** `kv-raft`, `kv-sim` and `kv-ring` must never gain
  tokio; CI enforces it. `kv-storage` has no tokio either and should not grow
  one — a `spawn_blocking`-cost benchmark belongs in `kv-node`.
- **`kv-raft`'s conformance suite must stay dependency-free.** If M11.5 wants
  `proptest` there, it moves to its own crate instead.
- **Both read engines.** CI runs the suite twice; keep the
  `BOHIME_READ_ENGINE=blocking` arm green.
- **Keep the `RwLock<HashMap>` arm.** The gate needs it as the comparison arm,
  behind a config flag.
- **Do not commit or push** unless the user asks.
- **Re-run the nemesis sweep** before claiming any `kv-raft` or `kv-sim`
  change safe. M11.5 should not touch either.

## Debts, unchanged by M11

1. **Nothing since M7 is committed** — four milestones in one pile.
2. **The 100k-seed nemesis sweep has not run since `6c704b9` (M7).** M8 and
   M9 changed `kv-raft`'s message shapes and commit path. ~15 min in release:
   `cargo nextest run --release -p kv-sim --run-ignored all -E 'test(nemesis_sweep_full)'`.
3. **The sweep does not cover snapshots at all.** `kv-sim` has zero references
   to snapshots — no compaction fault in the nemesis, nothing calls
   `take_snapshot`. Adding that fault first needs `invariants.rs` taught about
   `first_index`: `log_matching` and `leader_completeness` treat a compacted
   prefix as divergence and would report **false** violations. That is the
   prerequisite, and it is worth doing before M12 rather than after.
4. **`docs/DESIGN.md` and `CLAUDE.md` describe the single data group** — four
   Bitcask instances, `<data-dir>/raft`, "M0-M7 are done". Both are materially
   wrong about the architecture now and belong in whatever commit lands this.
5. **256 shards has never been measured under sustained write load**, nor with
   one shard snapshotting while 255 others tick.
