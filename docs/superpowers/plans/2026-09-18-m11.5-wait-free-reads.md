# M11.5 — Wait-free reads via `left-right`

`docs/DESIGN.md` §1.15 and the roadmap's M11.5 section are the spec.
`docs/superpowers/plans/2026-09-18-m11-handoff.md` is what this milestone was
handed: four of M11.5's assumptions had moved under it, and one measured
finding decided whether its headline gate could tell the truth.

## What M11.5 delivers

- `impl Absorb<KvOp> for KeyDir` — the Bitcask keydir behind `left-right`,
  swapped in behind M1.3's `KeyDirIndex` seam.
- `RwLock<HashMap>` kept as a first-class configuration (`--keydir locked`),
  which is the benchmark's comparison arm and an operator's escape hatch.
- A **published index** per Raft group, distinct from its applied index, that
  a confirmed read waits on instead.
- Reads resolved off the driver entirely: a pool of resolver tasks, each with
  its own `ReadView`, doing the keydir lookup the driver used to do.
- The measurement the gate asks for, and the honest reading of it.

## Decisions

### The writer needs a third thing, and §1.15 does not mention it

§1.15 argues Raft supplies left-right's three requirements for free — one
writer, a deterministic oplog, ops replayable twice. All true, and all
beside the point that bites first: **left-right's writer cannot read its own
unpublished writes.** `WriteHandle` derefs to a `ReadHandle`, which is the
*published* copy, and `append` only pushes onto the oplog — the write copy
does not see an op until the next `publish`.

The Raft apply loop is a read-modify-write loop. `Cas` reads the current
value. `session::cached` reads the last response for a `(client, sequence)`.
`apply_conf` reads the address book. With one publish per batch, entry N+1
would not see entry N, and `Cas` and the session table would both be wrong —
deterministically, on the first batch of two.

Three ways out, and only one is available:

- **publish per op** — correct, and throws away the batching §1.15 asks for;
- **mutate the write copy through `raw_write_handle`** — unsound. Readers may
  still be inside that copy after a swap, which is exactly what `publish`'s
  wait exists to prevent. (Ops are also idempotent enough here that
  double-application would be harmless — it is the data race that rules it
  out, not the arithmetic.)
- **an overlay**: a `HashMap<Vec<u8>, Option<ValueLoc>>` of the keys touched
  since the last publish. The writer's reads consult it first and fall through
  to the published copy; it is cleared on publish.

The overlay is what landed. It costs the delta rather than a third full copy,
so §1.15's "memory doubles" survives with an asterisk instead of becoming
"memory triples".

### The keydir seam was necessary and not sufficient

M1.3's five-method `KeyDirIndex` held exactly as promised: `put`, `get`,
`locate`, `scan`, `delete` and `compact`'s relocate loop are unchanged.

What it did not cover is that **a location is only meaningful together with
the segment map it was recorded in**. Compaction gives the merged segment the
smallest *retired* id — deliberately, so the merged data still sorts before
the active segment on the next replay. A reader on the outgoing keydir copy
that looked up the *current* segment map would therefore resolve an old offset
against the merged file and read whatever happens to live there.

That is not hypothetical: it is what the first implementation did, and
`a_reader_on_the_old_keydir_can_still_read_a_compacted_segment` caught it as
`Truncated { needed: 44, got: 24 }` — a record header read out of the middle
of someone else's record.

The fix is to put the segment map *inside* the published structure:
`KeyDir { entries, segments }`, with a `KvOp::Segments(Arc<SegmentMap>)`
flowing through the same oplog as every other change. Every reader's
(keydir, segments) pair is then consistent by construction, and a retired
segment's descriptor stays open for exactly as long as a copy names it —
no reference counting, no graveyard, no window. `Index::set_segments` is the
one call site `engine.rs` gained, and it is not a keydir operation, which is
why it sits on `Index` rather than in the trait.

### `try_publish`, not `publish`, and visibility can lag

`publish()` waits for readers to leave the copy it is about to overwrite. Its
only caller is the driver's `select!` loop — the loop this project has already
refused to block on a slow peer (M5's shedding) and on a disk read (M11's
`answer_read`). Blocking it on a *reader* would be the same mistake a third
time, and the failure mode is worse: a stalled drain misses ticks, and missed
ticks depose healthy leaders across every group on the node.

So `Engine::publish` uses `try_publish` and returns whether it succeeded. A
refusal is ordinary: the writes stay applied and invisible, `visible` does not
move, and the next drain tries again — and a drain happens every tick.

This is what makes the milestone's central window a *fact* rather than a race.
A read parked inside the published copy defers the swap for as long as it
likes, so the tests can hold the applied-but-not-visible window open and
assert on it deterministically, rather than looping and hoping.
`ReadViewFactory::hold_read_copy` is that hold, and it tests something real:
"a slow reader stalls the writer" is §1.15's own listed consequence.

### Where the factory lives, and why it is not the tonic service struct

Task 4 says "`ReadHandleFactory` in the service struct; a per-task
`ReadHandle`". The second half landed exactly; the first did not, and could
not without a protocol change.

A linearizable read needs a ReadIndex confirmation, and only the driver can
produce one. For `KvApi` to resolve a read itself, the driver would have to
answer a `Get` with "confirmed at index N" instead of a value — a new
`ClientReply` variant, threaded through ~25 call sites and the in-process
cluster harness, for no change in what is computed or where.

So the factory lives in `read_view.rs`'s resolver pool, which keeps the
property the task was after: a shared `Send + Sync` factory, a per-task
`!Sync` handle, and the keydir lookup off the driver. The driver's share of a
read is now one channel send.

**A pool, not a task per read.** Minting a `ReadView` registers an epoch slot
behind a mutex inside `left-right`. Doing that per read would put a mutex
acquisition back on every read — the exact cost this removes. Handles are
long-lived: one per (task, group), minted on first use.

## What landed

All five ✅ criteria. **396 tests pass** (was 378), on both read engines;
`cargo fmt --check` and `cargo clippy --workspace --all-targets -D warnings`
are clean; M4's 10k-seed election gate passes in 0.93s, unchanged. The `loom`
model is a separate build and run (`RUSTFLAGS="--cfg loom"`), 2 tests in
0.02s. `kv-raft` and `kv-sim` were not touched at all, so M11.5 adds nothing
to the nemesis-sweep gap M8/M9 carry.

18 tests are new: 12 in `kv-storage` (`tests::left_right`), 2 under loom, 5 in
`kv-node` (`tests::wait_free_reads`), less one that was rewritten rather than
added.

### The RED, which is the milestone

Written first, run against the naive `confirmed_at <= applied_index` wait:

```
thread 'tests::wait_free_reads::a_get_after_a_put_returns_never_misses_it'
panicked at crates/kv-node/src/tests/wait_free_reads.rs:63:5:
assertion `left == right` failed: a Get after a Put returned must not miss it
  left: None
 right: Some([118, 49])
```

`None` for a key whose `Put` had already returned `Applied`. Two of the other
three in that file failed the same way. Changing the wait to
`confirmed_at <= visible` turned all four green.

**One thing had to be removed to see it.** The resolver pool originally
*also* checked the invariant and answered `NotLeader` when it did not hold.
That is a defensible safety net and it made the bug invisible: the client's
retry loop swallowed the refusal, the read eventually succeeded, and the
regression test passed against the wrong wait. The check is now a `tracing::
error!` that does not change the answer. A second enforcement point for an
invariant is a second place for a regression to hide.

### Things that came out differently from the plan

**The writer needed an overlay, and the segment map had to join the keydir.**
Both are in "Decisions" above. Neither is in §1.15, and both are load-bearing:
without the first, `Cas` and the session table are wrong on the first batch of
two; without the second, a reader on the outgoing keydir copy reads an old
offset out of the merged segment file.

**`Engine` is `Send` but no longer `Sync`.** A left-right `ReadHandle` is
`!Sync`, so `&Engine` can no longer be shared across threads and two existing
tests and one benchmark stopped compiling. That is not a loss of concurrency —
it is the type system insisting each reader mint its own handle, which is what
makes the reads wait-free rather than merely lock-free. `Engine::get` is now
the owner's read; `ReadView::get` is everyone else's, and there can be any
number of those.

**The `ReadEngine` moved behind the resolver pool.** It used to be a field of
`Driver`, passed to each `Group::drain` as `&ReadEngine`. It is now an
`Arc<ReadEngine>` shared by the resolver tasks, because the thing that decides
to do a disk read is no longer the driver. `Driver::new`'s signature did not
change, so `main.rs`, `shards.rs` and the cluster harness are untouched by it.

**Task 4 landed as a resolver pool, not as a field of `KvApi`.** See "Where
the factory lives" above. `grep ReadHandle crates/kv-node/src/kv_service.rs`
finds nothing, deliberately.

### The benchmark measured misses, and said so at 60 Melem/s

The first version of `index_scaling.rs` reported left-right at 61.6 Melem/s on
one thread against `RwLock<HashMap>`'s 7.2 — an 8.5× single-thread advantage,
which no lock can explain. A fourth arm settled it: an **unsynchronised**
`Arc<HashMap>`, no lock at all, measured 6.0 Melem/s. left-right was ten times
faster than doing no synchronisation, which is not a result, it is a bug.

The cause: `with_writer.then(|| scope.spawn(move || ...))` moves the
`WriteHandle` into a closure that is *dropped where it is built* when
`with_writer` is false — and once the writer is dropped, `ReadHandle::enter()`
returns `None` forever. The no-writer left-right arm was timing 200k misses.

Two guards now: one thread owns the writer for the whole point whether or not
it writes, and each point probes three keys through the reader's own path both
before and after the timed region. The `plain_control` arm stays, because it
is what caught this and it is what any future number should be checked
against.

This is the M11 lesson again in a different costume: the suite was green, the
benchmark ran, and the number was fiction until something independent
contradicted it.

### The scaling numbers

`cargo bench -p kv-storage --bench index_scaling`, i9-12900H (6 P-cores + HT,
8 E-cores = 20 logical / 14 physical, so 20× never existed — a syscall-free
control tops out around 10-11×). 100k keys, random access, median of
criterion's estimate, **Melem/s**.

**Readers only:**

| threads | 1 | 2 | 4 | 8 | 16 | 20 | 1→20 |
|---|---|---|---|---|---|---|---|
| `plain_control` (no sync) | 8.20 | 19.74 | 39.80 | 54.22 | 91.17 | 83.14 | **10.1×** |
| `left_right` | 6.17 | 15.32 | 24.88 | 45.49 | 82.05 | 79.33 | **12.9×** |
| `dashmap` | 7.44 | 13.77 | 26.92 | 36.80 | 59.58 | 52.57 | 7.1× |
| `rwlock` | 7.00 | 11.41 | 10.46 | 8.58 | 7.29 | 6.74 | **0.96×** |

`left_right` reaches **90% of doing no synchronisation at all** at 16 threads,
and is the only arm that tracks the control's shape. `rwlock` **peaks at two
threads and then goes backwards** — 20 threads is slower than one. `dashmap`
scales but plateaus around 60% of the control.

Both `plain_control` and `left_right` dip from 16 to 20 threads, which is the
machine rather than the index: the last four logical CPUs are hyperthreads on
already-busy P-cores.

**With one thread writing continuously** — the case the three actually differ
in, and the one a Raft apply loop produces. The writer here publishes every 64
ops, which is far more aggressive than the driver's once-per-drain, so this is
left-right's pessimistic case:

| threads | 1 | 2 | 4 | 8 | 16 | 20 | 1→20 |
|---|---|---|---|---|---|---|---|
| `left_right` | 5.80 | 12.30 | 23.12 | 34.12 | 62.62 | 59.38 | **10.2×** |
| `dashmap` | 6.98 | 13.64 | 24.83 | 36.70 | 58.43 | 56.86 | 8.1× |
| `rwlock` | 4.35 | 6.84 | 6.98 | 6.75 | 6.89 | 6.77 | **1.6×** |

`rwlock` is flat at ~6.8 Melem/s from four threads: adding cores buys nothing
once a writer is in the mix, because every reader queues on the one lock the
writer keeps taking exclusively. left-right is **8.8× faster at 20 threads**
than the implementation it replaces, and is unaffected by the writer's
presence in shape — it loses ~25% of the reader-only figure, all of it the
core the writer is using.

`dashmap` is the honest surprise: within noise of left-right up to 8 threads
and behind it past that. It would be a defensible choice, and it is the one
this design should be prepared to be asked about. What it does not offer is
what M11.5's correctness story is built on — a *snapshot*: a `DashMap` read
sees each shard's lock independently, so a reader can observe a batch half
applied. left-right's readers cannot, which is why "visible up to index N" is
a statement that can be made at all.


### What this says about §1.15's "scale linearly with cores"

Half right, and the half that is wrong is the half the README would have
quoted.

**Right about the keydir.** left-right is the only arm whose read throughput
keeps climbing with cores while a writer is running, and the only one that
costs a reader nothing when the writer is busy. `RwLock<HashMap>` does not
scale at all under a writer — it is flat-to-falling from two threads, because
every reader queues behind the same lock and the writer's exclusive
acquisition drains the queue. That is the comparison the milestone exists to
make, and it makes it.

**Wrong about reads.** §1.15 says reads "scale linearly with cores". The
keydir lookup is one part of a read; the other is a `pread`, and that part is
capped at ~6.4M reads/s on this machine however many cores are added, because
every reader goes through one shared `struct file` per segment (`fget` on
`f_count`, plus the per-handle `f_ra`). The read-path handoff measured it
directly: one fd each reaches ~16.8M, one file each ~17.4M, one shared `File`
**6.4M and flat from 8 threads**.

So the keydir is no longer the ceiling — and it was not the ceiling before
this milestone either. **Per-reader file handles matter more to end-to-end
read throughput than left-right does**, and nothing in M11.5 changes that. A
scaling graph of `Engine::get` would still be flat, and it would still be flat
for all three arms, which is why `index_scaling.rs` measures the index alone
and says in its own header why.

**Recommendation, for the user to decide.** The README graph should be the
index graph, captioned as the index's, with the file-handle ceiling named
beside it — not a whole-read graph that would be a picture of a file
descriptor. Fixing the handle (a `dup`'d fd per reader task, or `io_uring`
with `IORING_REGISTER_FILES`, which `read_engine.rs` currently does not use)
is a real ~2.6× on the read path and is a milestone of its own, not a
footnote to this one. `README.md` and `docs/DESIGN.md` are untouched here.

## Not done, deliberately

- **`ReadHandleFactory` in the tonic service struct.** The factory is in the
  resolver pool instead; see "Where the factory lives". Reaching the service
  needs `ClientReply::ReadAt { index }` and a per-group visibility handle in
  `KvApi` — a protocol change for no change in what is computed.
- **The file-handle ceiling.** Named, measured by the preceding milestone, and
  left alone: it is not the keydir, and deciding it belongs in M11.5 is the
  user's call, not this milestone's.
- **`Engine::locate`'s `Arc<SegmentMap>` clone**, which the handoff flagged as
  a second self-inflicted ceiling at ~14.7 Mops/s from 8 threads. It stopped
  being a shared refcount by accident: the segment map now lives inside the
  published `KeyDir`, so a reader clones the `Arc` out of its own copy's
  field. Not measured after the change, so it is named rather than claimed.
- **Session-table reads still go through the engine's writer path**, because
  they happen inside `apply`. That is correct and cannot be otherwise — the
  apply loop must see its own writes — but it does mean the session table gets
  no benefit from left-right.
- **`docs/DESIGN.md` and `CLAUDE.md` are still wrong about the architecture**
  (M10's four-Bitcask story, "M0-M7 are done"), and §1.15 is now wrong in the
  three specific ways above. Untouched by instruction.
