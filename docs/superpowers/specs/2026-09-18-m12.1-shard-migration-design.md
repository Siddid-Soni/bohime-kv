# M12.1 — Shard migration

`docs/DESIGN.md` §1.12 and the roadmap's M12 section are the spec. M12 as
written is two subsystems behind one gate — a migration driver and a Merkle
verifier — and this document covers only the first. M12.2 (Merkle trees,
`VerifyShard`, the corruption test) gets its own design, and it is the thing
that finally verifies what M12.1 moves.

The split is not cosmetic. "Data rebalances, no request fails" and "every
replica agrees on its Merkle root" are separately testable claims, and folding
them into one plan means the second half cannot be exercised until the first
lands. M11 and M11.5 were split for the same reason.

## What M12.1 delivers

- A node added to a live cluster **receives shards**. Today it receives
  nothing: `ShardSupervisor` founds groups once from map version 1, and a
  `--join` node founds nothing at all, so the map places shards on it that it
  never hosts.
- A node whose shards the map has moved away **stops hosting them and reclaims
  their disk**.
- Both, driven by the four-step sequence §1.12 names — learner-add, catch-up,
  promote, remove — with no custom data-movement protocol. M8's snapshot
  machinery already moves the data.
- A rate limit, because moving many shards at once is how a rebalance becomes
  an outage.

Not in M12.1: `VerifyShard`, Merkle trees, and any repair path. Not in M12 at
all: changing `num_shards`, splitting or merging shards, and cross-shard
anything.

## The truth model

**The map is the target. Each shard group's own Raft config is the state.**

There is no new replicated state and no migration plan recorded anywhere. A
shard is mid-migration exactly when its group's committed config differs from
`map.replicas(shard)`, and that condition is already visible in
`ClusterStatus` — an operator reads it, and so does the reconciler.

The alternative was an explicit `pending: Vec<Move>` list inside `ShardMap`,
which `docs/DESIGN.md:290` anticipates ("an explicit map gives you a place to
put that state") and `kv-ring/src/map.rs`'s header repeats. It buys
cluster-wide rate limiting and a single readable rebalance status. It costs a
second replicated structure that has to stay consistent with the first, plus a
completion-reporting path across nodes: the leader of shard 37 is not
generally the meta leader, so "this move is done" would need an admin RPC from
one to the other. The condition we need is already derivable from two things
every node has. Deriving it is cheaper than replicating it.

What this gives up is worth naming: there is no single value an operator can
read that says "the rebalance is 60% done". They read it by diffing shard
configs against the map across nodes, which `ClusterStatus` supports and no
tooling presents yet. If M13 wants a progress bar, the `pending` list is where
it goes.

## Components

### 1. The reconciler — `crates/kv-node/src/migrate.rs`

A per-node task, sibling of `MetaReconciler` and `ShardSupervisor`, on the same
deliberately slow loop (500 ms). Placement changes when an operator adds a
machine; the cost of noticing one a second late is nothing, and the cost of
polling a driver hard is paid on every node forever.

One pass:

1. Load the published map. `None` — the meta group is still electing — returns.
2. Ask the shard driver for `ShardStatuses`.
3. For each shard **this node leads**, compare the group's members against
   `map.replicas(shard)` and take at most one step:
   - a node in the map that the group does not contain → `AddNode { id,
     address }` addressed to `group::shard(s)`;
   - a voter the group contains that the map does not name → `RemoveNode
     { id }`, **but only once every node the map names is a voter**.
4. Promotion is not this task's job. `Group::maybe_promote` already promotes a
   learner whose `match_index` reaches the commit index, which is the whole
   reason a node joins as a learner.

**Add before remove, never the reverse.** Removing first would drop the group
to two voters of three before the third arrives, so a single further failure
takes the shard down — a rebalance that manufactures the unavailability it
exists to avoid. Waiting for *every* incoming replica to be a voter before
removing anything is the same rule applied to a multi-slot move.

**No new admin ops.** `AdminOp::AddNode`/`RemoveNode` already propose exactly
these conf changes, and `AdminRequest` already carries the group id, so the
reconciler is a caller of machinery M9 built rather than a second
implementation of it. `RemoveNode` even picks `RemoveVoter` vs `RemoveLearner`
from the live config, which is what a migration aborted halfway needs.

`ShardStatus` gains `learners: Vec<NodeId>`. It reports `replicas` (the
group's voters) today, and a reconciler that cannot see learners would propose
`AddLearner` for a node that is already one on every pass until it is
promoted — a conf entry per pass, all of them refused.

**Rate limit.** `--max-migrations`, default 4. Stated precisely, because
"four at a time" has two readings: **in one pass, the reconciler takes the
diverging shards it leads in shard-id order and acts on at most
`--max-migrations` of them.** Divergence persists until the move completes, so
the same shards are chosen on the next pass and the in-flight count is capped
at four by construction — no separate bookkeeping of what is outstanding, and
the choice is deterministic, which is what makes the limit testable. A node
leading 154 shards moves four at a time. The limit is per node rather than per
cluster because the
expensive half of a move is one receiver's snapshot ingest and Bitcask open,
and a per-node cap on each side bounds that without anybody coordinating.

**Who runs it.** Every node, like the other two reconcilers. A node acts only
on shards it leads, so the work partitions itself and a node that leads
nothing does nothing.

### 2. Adoption — `crates/kv-node/src/shards.rs`

`report_divergence`'s first branch — "the map places this shard here but it is
not hosted (M12)" — stops warning and starts acting. The supervisor opens the
shard and hands the `Group` to the driver exactly as founding does.

**It must force `initial_learner: true` and `peers: []`, overriding the node's
own flags.** This is the one place M12.1 can produce split brain, and it does
it quietly:

`open()` builds the core config from `config.raft_config_for(group)`, whose
`peers` is the node's entire `--peer` list and whose `initial_learner` is the
node's `--join` flag. On a founder that flag is false, so `initial_cluster`
(`kv-raft/src/node.rs:1337`) would make the adopting node a **voter** in a
fabricated config containing every node the operator ever named. Nothing stops
a voter campaigning. It would win an election in its own fabricated group and
become a second leader for a shard that already has one, with a log that
shares no history with the real one.

Forced to `{ voters: {}, learners: {me} }` it cannot campaign
(`node.rs:564` returns early for a non-voter) and cannot vote (`node.rs:657`
requires `is_voter(self)`), so it sits inert until the leader contacts it.
The real config then arrives by one of two paths, both of which exist:

- **InstallSnapshot.** M8 stamps `ClusterConfig` into the snapshot precisely
  so a node caught up this way learns the membership with the state, and
  `RaftNode::new` prefers the snapshot's config over the bootstrap one.
- **The conf entry in the log tail**, whose `context` carries the whole
  address book (M9), which is also how the adopting node learns where its new
  peers live.

**No address seeding is needed**, and this is worth stating because it looks
like it should be: an adopted group's `endpoints` book starts empty, and a
node with no addresses cannot dial anybody. It does not have to. A Raft reply
travels back on the same gRPC call (`RaftServer::exchange`), so a follower
never dials its leader — only a candidate and a leader dial, and an adopted
group is neither until its real config has arrived.

**Throttling.** Adoption is already serialized: the supervisor opens one shard
at a time on a blocking thread. The sender-side `--max-migrations` bounds how
many arrive.

**Ordering against the leader.** Both sides are driven by the same published
map, so the leader proposes `AddLearner` for node 4 and node 4 adopts the
shard on the strength of the same map version. Neither waits for the other: a
message for a group not yet adopted is answered `not_found` and the peer
retries on its next heartbeat, which is what `GroupRegistry`'s two rejection
codes already document.

### 3. Departure — `shards.rs` and `driver.rs`

A shard leaves this node when **two independent witnesses agree**:

1. the group's own committed config no longer contains this node, and
2. the published map no longer places the shard here.

Then, in order: the driver drops the `Group` (stopping its tick and its
apply), `GroupRegistry::unregister` stops routing to it, and the directories
`shards/{id:05}/raft` and `shards/{id:05}/state` are removed.

Two witnesses because either alone is transiently wrong in normal operation
and the act is unrecoverable. A map is stale on any node that has not yet
applied the latest version — routinely, since the reconciler publishes on a
500 ms loop. A group's config is stale on a node that is behind on its log,
and is *briefly fabricated* on one that has just adopted. Deleting a shard's
data on one witness means deleting it on a node that is merely behind.

**The empty-adoption case.** A group adopted but never contacted holds the
fabricated `{voters: {}, learners: {me}}` config, which is not a committed one
and does name this node. Read literally, witness 1 never fires and a shard
adopted by mistake — the map moved again before the leader added us — is never
reclaimed. So the rule is stated as: *the group's committed config excludes
this node, where a group that has committed nothing counts as excluding it.*
A group that has committed nothing also holds nothing, so the delete is
trivially safe.

**When the departing node is the leader**, the core already handles it:
`RaftNode` hands off to a remaining voter the moment it finds itself no longer
a voter (`node.rs:1224`), so removing a leader costs a handoff rather than an
election timeout. The reconciler needs no special case, and M9's gate already
covers the equivalent for the meta group.

### 4. `AdminService::Rebalance`

Stops answering `unimplemented`. It runs one reconciler pass immediately and
answers with the number of shards currently diverging from the map on this
node. It is a *nudge*, not a command: the reconciler runs on its own loop
regardless, and an operator who has just added a node wants the pass now rather
than within 500 ms. `RebalanceResponse` gains that count so the call says
something an operator can act on.

## The prerequisite: a founded group's voter set does not survive a restart

`shards::open` passes no voters on reopen, so the core config comes from
`raft_config_for`: `peers = <every --peer>`, `initial_learner = false`.
`RaftNode::new` consults that bootstrap config whenever there is **no snapshot
and no conf entry in the live log** — which is exactly the state of a founded
shard group that has never had a membership change.

So a restarted node in a 5-node cluster with RF 3 may reopen shard 7 believing
all five nodes are voters when its replica set is three: quorum 3 instead of 2,
and two members that never answer. RF equal to the node count hides it
completely, which is why nothing in the suite catches it.

This is stated as a hypothesis, not a finding — it has not been reproduced yet.
The first task of the plan is the failing test: a 5-node RF-3 cluster,
restart one node, assert the shard's committed config is unchanged. Confirm it
fails for that reason before fixing anything.

**The fix, if it reproduces:** `shards.rs` writes the founding voter set beside
the group as `shards/{id:05}/.voters` at founding time, mirroring how
`.placement` records the founding map version, and passes it as `peers` on
reopen. Node-side, so `RaftStorage` and its conformance suite are untouched.
The bootstrap config is only ever the *base* that `replay_conf` layers conf
entries onto, so a `.voters` file that predates a migration is still correct:
the entries that moved the shard are in the log above it.

The alternative — a `\x00conf` key in `BitcaskStorage` beside `\x00hard_state`
— puts the config where the core would read it directly, which is arguably
where it belongs. It is rejected here because it extends `RaftStorage`, and
therefore the conformance suite and `MemStorage`, for a problem whose cause is
entirely in the node's bootstrap path.

## Gate

`tests::migrate::the_m12_1_gate` — three nodes, RF 3, four shards, a
continuous writer. Admit a fourth node. Assert:

- no client request fails for the duration;
- every shard's committed group config converges to `map.replicas(shard)`;
- every key written before the move is readable from the new replica.

Merkle-root agreement is M12.2's half of §M12's ✅, and this gate asserts
value-level agreement in its place by reading each replica's engine directly.

Supporting tests, each pinning one trap named above:

- `a_founder_adopting_a_shard_never_becomes_its_voter` — the campaign trap.
  Written against the unforced config first, watching it produce a second
  leader.
- `a_shard_is_deleted_only_when_both_witnesses_agree` — a stale map alone does
  not delete a group whose config still names this node; both together do.
- `an_adopted_group_that_was_never_contacted_is_reclaimed` — the
  empty-adoption case.
- `a_replica_is_never_removed_before_its_replacement_votes` — the
  add-before-remove ordering, observed across the conf entries the group
  commits.
- `at_most_max_migrations_move_at_once` — the rate limit.
- `a_founded_groups_voters_survive_a_reopen` — the prerequisite.

Still green, unchanged: M11's gate (`tests::multi_raft::the_m11_gate`), M10's
(`tests::ring::the_m10_gate`), M9's (`tests::membership::the_m9_gate`), M6's
three-process gate, and the whole suite under `BOHIME_READ_ENGINE=blocking`.

`kv-raft` and `kv-sim` are not touched by this milestone, so the 100k-seed
nemesis sweep's four-milestone debt (`docs/KNOWN-ISSUES.md` §4) neither grows
nor is discharged here.

## Risks

- **A shard that never converges.** A group whose leader keeps changing, or
  whose learner never catches up, leaves a divergence the reconciler retries
  forever. It is not wrong — the map stays published and the old replicas keep
  serving — but it consumes one of the `--max-migrations` slots indefinitely
  and nothing says so. Mitigation for M12.1 is a log line naming the shard and
  how long it has diverged; a real fix is M13's operational surface.
- **Adoption opens Bitcask instances on a supervisor that also founds.** A node
  adopting 60 shards does 120 `open`s serialized behind each other. That is
  the intended throttle, but it means the last shard adopted waits for all the
  others. Acceptable while `--max-migrations` is small, and worth measuring.
- **`--max-migrations` interacts with `peer_queue_depth`.** M11 derived the
  per-peer queue depth from `num_shards` because a queue that cannot hold one
  message per group sheds somebody's every drain. Migration adds snapshot
  traffic to the same links. Not expected to matter at four concurrent moves,
  but it is the shape of problem M11 already hit once.
